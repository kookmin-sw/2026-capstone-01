# Krip Frontend AI Agent Rules

이 문서는 Krip 프론트엔드에서 작업하는 모든 AI Agent가 **매 작업 시작 전에 반드시 읽고 준수해야 하는 상시 명세**다. 특정 기능의 요구사항이 이 문서보다 구체적이면 해당 요구사항을 함께 적용하되, 충돌하거나 불명확하면 임의로 결정하지 말고 사용자에게 확인한다.

## 1. 프로젝트 이해

- 서비스명: **Krip**
- 목적: 외국인 여행자가 서울 관광을 한 곳에서 준비하고 경험할 수 있는 올인원 플랫폼
- 핵심 기능: 위치 기반 관광지 탐색, AI 맞춤 일정, 수동 일정 작성, 여행 메이트 매칭, 친구 관리, 실시간 채팅, 피드 및 알림
- 주요 사용자: 한국어와 서울의 지리·문화·행정 체계에 익숙하지 않을 수 있는 외국인
- 팀 구성: **Frontend 3명, Backend/AI 1명**
- 프론트엔드 기술: React, TypeScript, Vite, React Router, Fetch API, Firebase, Capacitor, ESLint

Agent는 기능의 동작 여부뿐 아니라 외국인 사용자의 이해 가능성, 모바일 사용성, 다국어 확장성, 위치·개인정보 보호를 제품 품질의 일부로 취급한다.

## 2. 지시 우선순위

다음 순서로 지시를 적용한다.

1. 사용자가 현재 작업에서 명시한 요구사항
2. 이 문서와 작업 경로에 있는 더 구체적인 규칙 문서
3. 저장소의 기존 코드, 디자인 시스템, API 계약 및 팀 관례
4. 일반적인 React·TypeScript 모범 사례

충돌이 발견되면 숨기지 말고 설명한다. 데이터 손실, API 계약 변경, 광범위한 구조 변경처럼 영향이 큰 선택은 작업 전에 승인을 받는다.

## 3. 작업 시작 프로토콜

Agent는 코드를 수정하기 전에 반드시 다음을 수행한다.

1. 이 문서를 끝까지 읽는다.
2. 사용자 요청을 목표, 작업 범위, 완료 조건으로 나누어 이해한다.
3. 관련 파일과 호출 흐름을 먼저 탐색한다. 파일명만 보고 구현을 추측하지 않는다.
4. `package.json`, ESLint·TypeScript 설정, 기존 컴포넌트와 유사 구현을 확인한다.
5. 현재 Git 변경 사항을 확인하고 다른 팀원의 수정 내용을 보존한다.
6. 요구사항이 모호하더라도 안전하고 되돌릴 수 있는 범위에서는 합리적으로 진행한다. 결과를 크게 바꾸는 불확실성만 질문한다.
7. 작업 시작 응답에서 **“AI_RULES.md 확인 완료”**라고 밝히고, 이해한 범위와 검증 계획을 짧게 알린다.

## 4. 작업 원칙

- 요청받은 문제를 해결하는 데 필요한 최소 범위만 수정한다.
- 관련 없는 리팩터링, 파일 이동, 패키지 추가, 포맷 전체 변경을 섞지 않는다.
- 기존 동작과 공개 인터페이스를 기본적으로 보존한다.
- 증상만 가리는 예외 처리보다 원인을 찾아 수정한다.
- 새 구현 전에 재사용 가능한 컴포넌트, 훅, 유틸리티, 타입, 스타일이 있는지 찾는다.
- 복잡한 작업은 작은 단위로 나누고 각 단위를 검증한다.
- 사용자의 코드나 다른 팀원의 변경을 임의로 삭제하거나 되돌리지 않는다.
- 생성 파일, 빌드 산출물, 비밀 정보는 커밋 대상에 포함하지 않는다.
- 확신할 수 없는 사실이나 실행하지 않은 검증을 완료한 것처럼 보고하지 않는다.

## 5. React·TypeScript 규약

### 5.1 타입과 네이밍

- 새 코드는 TypeScript로 작성하고 `any` 사용을 피한다. 불가피하면 범위와 이유를 명시한다.
- 타입 추론이 명확한 지역 변수까지 중복 표기하지 않는다. 함수 경계, API 응답, 공유 상태처럼 계약이 되는 지점은 명시적으로 타입을 선언한다.
- 컴포넌트와 타입은 `PascalCase`, 함수·변수·훅은 `camelCase`, 상수는 의미가 분명할 때 `UPPER_SNAKE_CASE`를 사용한다.
- 축약어보다 역할이 드러나는 이름을 사용한다. boolean은 가능하면 `is`, `has`, `can`, `should`로 시작한다.
- 단위가 있는 값은 이름에 단위를 포함한다. 예: `timeoutMs`, `distanceKm`.

### 5.2 컴포넌트와 상태

- 컴포넌트는 하나의 명확한 책임을 갖게 한다. 큰 화면은 의미 있는 섹션이나 기능 단위로 분리한다.
- 파생 가능한 값은 별도 state로 중복 저장하지 않는다.
- `useEffect`는 외부 시스템과의 동기화에 사용하고, 단순 계산에는 사용하지 않는다.
- Effect의 의존성과 cleanup을 정확히 관리한다. 타이머, 이벤트 리스너, 구독은 반드시 정리한다.
- Hook을 조건문이나 반복문 안에서 호출하지 않는다.
- 성능 최적화는 측정 가능한 필요가 있을 때 적용한다. 습관적인 memoization으로 코드를 복잡하게 만들지 않는다.
- 로딩, 빈 결과, 오류, 성공 상태를 명시적으로 처리한다.

### 5.3 구조와 스타일

- Layered 구조의 책임을 따른다: `app`은 앱 조합·라우팅·공통 레이아웃, `pages/<domain>`은 Route Page, `features/<domain>`은 사용자 기능과 상태·전용 UI, `shared`는 여러 계층이 함께 쓰는 UI·데이터·범용 로직, `api`는 서버 통신, `lib`는 Firebase 같은 외부 서비스 연동에 사용한다.
- 의존 방향은 `app → pages → features → shared`를 기본으로 한다. 하위 계층이 상위 계층의 Page나 App을 import하지 않는다.
- 새 페이지는 `pages/<domain>`에 배치한다. 한 기능에서만 쓰는 컴포넌트를 `shared`로 올리지 않는다.
- import 방식, 따옴표, 세미콜론, 들여쓰기는 수정 대상 주변 코드와 ESLint 설정을 따른다.
- 긴 함수는 줄 수가 아니라 책임과 테스트 가능성을 기준으로 분리한다.
- 주석은 코드가 무엇을 하는지 반복하지 말고, 비즈니스 제약·예외·결정 이유를 설명할 때만 작성한다.
- 화면에 표시되는 텍스트를 로직 곳곳에 중복하지 않고 다국어 리소스로 이동하기 쉬운 형태로 둔다.

## 6. 사용자 경험, 다국어 및 접근성

- 외국인 사용자가 이해하기 쉬운 간결한 문구를 사용하고, 한국인만 아는 약어·행정용어·문화적 전제를 피한다.
- 날짜, 시간, 통화, 거리, 주소 형식은 locale과 timezone을 고려한다. 서버 시각과 사용자 현지 시각을 혼동하지 않는다.
- 장소명과 주소는 번역 과정에서도 원문 식별이 가능하도록 데이터 구조를 보존한다.
- 색상만으로 상태를 전달하지 않는다.
- 모든 상호작용 요소는 키보드로 접근 가능해야 하며 적절한 semantic HTML을 우선한다.
- 이미지에는 목적에 맞는 대체 텍스트를 제공한다. 장식 이미지는 스크린 리더에서 제외한다.
- 입력 요소에는 연결된 label, 오류 설명, 유효한 autocomplete 및 적절한 모바일 input type을 제공한다.
- 모달·토스트·동적 콘텐츠는 포커스와 스크린 리더 알림을 고려한다.
- 모바일 우선으로 구현하고 작은 화면, 긴 번역 문자열, 글자 확대, safe area를 확인한다.

## 7. API, 데이터 및 Backend/AI 협업

- API URL, 요청·응답 타입, 인증 방식, 오류 형식을 기존 계약과 대조한다. 추측으로 필드를 만들지 않는다.
- API 변경이 필요하면 Frontend 3인과 Backend/AI 1인이 병렬 작업할 수 있도록 변경 전후 계약과 영향 범위를 명확히 기록한다.
- 네트워크 요청은 로딩, 실패, 재시도 가능성, 요청 취소 또는 오래된 응답 경쟁 상태를 고려한다.
- 사용자에게 기술적인 서버 오류를 그대로 노출하지 않는다. 진단 정보와 사용자 메시지를 분리한다.
- AI 추천 결과는 지연, 부분 응답, 빈 결과, 잘못된 형식이 올 수 있다고 가정하고 안전하게 검증한다.
- AI 생성 콘텐츠를 확정 사실로 표현하지 않는다. 영업시간·가격·이동 시간처럼 변할 수 있는 정보는 출처나 갱신 시점을 고려한다.
- 프론트엔드 타입 변경만으로 서버 계약이 변경되었다고 간주하지 않는다.

## 8. 보안과 개인정보

- 비밀번호, API 키, access/refresh token, 개인 식별 정보, 정확한 위치를 코드·로그·오류 메시지에 노출하지 않는다.
- 비밀 값을 `VITE_` 환경 변수에 두면 브라우저 번들에 공개된다는 점을 인지한다. 비밀 키는 Backend가 관리한다.
- 인증·인가 검사는 UI 숨김만으로 대체하지 않는다. 보호가 필요한 작업은 서버 검증을 전제로 한다.
- 사용자 입력과 외부 HTML을 신뢰하지 않으며 `dangerouslySetInnerHTML` 사용을 피한다.
- 위치, 알림, 카메라 등 권한은 필요한 시점에 목적을 설명하고 요청한다. 거부 상태에서도 앱이 안전하게 동작해야 한다.
- 로그아웃·탈퇴·토큰 만료 시 민감한 로컬 상태와 구독을 적절히 정리한다.
- 의존성 추가는 유지보수성, 번들 크기, 라이선스, 보안 영향이 정당할 때만 제안하거나 수행한다.

## 9. Git과 협업 규약

- 작업 전후 `git status`와 diff를 확인한다.
- 다른 사람의 변경을 덮어쓰거나 자동으로 되돌리지 않는다.
- 한 변경에는 하나의 목적만 담고, 리뷰 가능한 크기를 유지한다.
- 사용자 요청 없이 commit, push, merge, rebase 또는 브랜치 변경을 하지 않는다.
- lockfile은 의존성이 실제로 바뀔 때만 수정한다.
- API·환경 변수·설정·라우트처럼 팀에 영향을 주는 변경은 완료 보고에 별도로 명시한다.
- 충돌 가능성이 큰 공용 파일을 수정했다면 그 사실과 변경 이유를 알린다.

## 10. 검증 기준

변경 후 영향 범위에 비례하여 다음을 수행한다.

```bash
cd frontend
npm run lint
npm run build
```

- 가능하면 변경 기능의 핵심 사용자 흐름을 직접 확인한다.
- 기존 테스트가 있으면 관련 테스트를 실행한다. 버그 수정 시 재현 가능한 테스트를 우선 고려한다.
- UI 변경은 최소한 모바일·데스크톱 레이아웃, 로딩·빈 상태·오류 상태, 키보드 접근을 확인한다.
- 검증 실패를 숨기지 않는다. 이번 변경 때문인지 기존 문제인지 구분하고 오류 내용을 요약한다.
- 문서만 수정한 경우 빌드가 실질적 검증이 아니면 생략할 수 있으며, 생략 이유를 보고한다.

## 11. 금지 사항

- 요청과 무관한 대규모 리팩터링
- 사용자 승인 없는 파괴적 Git 명령 또는 데이터 삭제
- 린트·타입 오류를 규칙 비활성화, 무분별한 type assertion, `@ts-ignore`로 은폐
- 실제 데이터가 필요한 기능에 임시 mock·하드코딩 값을 남김
- API 키, 토큰, 개인정보, 내부 URL을 코드나 답변에 노출
- 검증하지 않은 라이브러리 API나 서버 계약을 사실처럼 가정
- 실패를 삼키는 빈 `catch` 또는 원인 없는 fallback
- 접근성 의미를 훼손하는 `div` 기반 버튼과 클릭 처리
- 사용자가 요청하지 않은 dependency, 설정, 공개 API 변경
- 실행하지 않은 테스트를 통과했다고 보고

## 12. 완료 보고 형식

작업이 끝나면 다음을 간결하게 보고한다.

1. 변경한 내용과 이유
2. 주요 변경 파일
3. 실행한 검증과 결과
4. 남은 제약, 미검증 항목 또는 팀이 알아야 할 계약 변경

문제가 남아 있으면 완료라고 표현하지 않는다. Agent의 목표는 많은 코드를 작성하는 것이 아니라, 팀원이 이해하고 검토하며 안전하게 이어서 작업할 수 있는 변경을 만드는 것이다.

## 13. 작업 이력 기록

- 코드·설정·구조·문서를 변경한 작업은 완료 전에 `frontend/AI-RULES/WORK_LOG.md`에 기록한다.
- 최신 작업을 문서 상단에 추가하고, 날짜와 작업 제목을 명시한다.
- 각 기록에는 요청 목적, 주요 변경 내용, 변경 파일 또는 디렉터리, 검증 결과, 남은 경고·제약 사항을 포함한다.
- 실행하지 않은 검증을 기록하지 않으며 실패나 미검증 항목을 숨기지 않는다.
- 단순 질의응답이나 파일 변경이 없는 조사 작업은 기록을 생략할 수 있다.
- 비밀번호, 토큰, API 키, 개인정보 및 내부 전용 주소는 작업 이력에 기록하지 않는다.

## 작업 전 체크리스트

- [ ] `AI_RULES.md`를 읽었다.
- [ ] 요청의 목표·범위·완료 조건을 이해했다.
- [ ] 관련 코드와 기존 패턴을 확인했다.
- [ ] 현재 변경 사항을 확인하고 보존했다.
- [ ] 다국어·접근성·모바일·보안 영향을 검토했다.
- [ ] 변경 후 lint/build 및 관련 흐름을 검증할 계획이 있다.
- [ ] 변경 작업 완료 후 `WORK_LOG.md`에 결과를 기록한다.
